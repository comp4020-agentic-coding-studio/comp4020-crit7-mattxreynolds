# Triage: new bugs and requests only

Scope: issues labelled `needs-triage` (`gh issue list --label needs-triage`),
or the one given. Decision issues and slices are planned work, not triage.

For each issue:

1. **Verify before judging.** A bug: reproduce it at the current SHA (the
   built server, `pnpm e2e`, or a failing spec test) and note exactly what you
   saw. A request: check it against the published spec, the open spec issue,
   `docs/decisions/` and the map's out-of-scope list.
2. **Propose a state** in a comment whose first line is
   `> *This was generated by AI during triage.*`:
   - `ready-for-agent`: a reproduced bug that breaks an existing acceptance
     line or decision. Add acceptance lines, a proposed seam, `slice`, and
     `--parent <spec>` if it belongs to one. Claude may apply this label.
   - `needs-info`: the question that blocks triage, addressed to whoever can
     answer. Claude may apply this label.
   - **New product behaviour or `wontfix`**: that is Matt's decision. Give the
     recommendation and reason, and wait for his answer before labelling. A
     new behaviour he wants becomes a decision issue on the map, not a slice.
3. Remove `needs-triage` once a state is applied. Never close issues; a
   `wontfix` Matt agrees to is his to close.

Commit nothing unless a failing test that reproduces a bug is worth keeping;
then commit it with `Refs #N` on the issue that will fix it.
